# Limits and honest notes

Read this before you trust Ringlark with real people. Everything here was run on the date shown (2026-11-23) unless it says UNVERIFIED. The Python test and coverage numbers were measured again on 2026-11-26 for version 1.0.1 (that run included the SQLite migration cycle). The Postgres migration cycle was skipped in that run (no `TEST_POSTGRES_URL`) and the browser tests were not run again either.

## What was run

- <!--n:tests.passed-->530<!--/n--> Python tests pass (that includes the <!--n:core_tests-->87<!--/n--> tests of the shared core package, which `pytest.ini` collects) and <!--n:tests.skipped-->1<!--/n--> is skipped (the Postgres cycle, which needs `TEST_POSTGRES_URL`). Line coverage of the `ringlark` package is <!--n:tests.coverage_percent-->91<!--/n--> percent (`pytest --cov=ringlark`). The weakest files are the worker (`worker.py`) and the email adapter (`adapters/smtp_imap.py`); their per file percentages were not measured again. <!--n:contract_tests-->12<!--/n--> contract tests check the adapters against saved excerpts of the vendors' public docs.
- Compliance property tests make thousands of random worlds and check that the dialer never calls outside the person's hours, never calls a do not call or revoked consent number, never goes over the cap, and never places a call without the AI disclosure. They run on the pure rules and on the real database path.
- Browser tests (Playwright, Chrome) run the whole demo path, axe accessibility checks on all 11 pages in light and dark with zero serious or critical findings, keyboard use, reduced motion, 5,000 call rows, layout shift, console errors, and 8 screenshots states at 1440 by 900 and 390 by 844.
- `tools/score_seed.py`: all 7 planted problem types are held back (19 rows).
- Migrations: up, down and up again on SQLite with no drift. The same cycle also passed on Postgres 17.7 in a throwaway local cluster (`TEST_POSTGRES_URL`). The rest of the app was not run against Postgres by an automated test.

## What was NOT run (UNVERIFIED)

- **Any real Telnyx, Ultravox, Cal.com or Twenty account.** The adapters are tested against local copies written from the public docs.
- **The Telnyx to Ultravox bridge.** Ringlark creates the Ultravox call with a Telnyx medium, dials with Telnyx Call Control, and joins the audio with a `streaming_start` action. The action paths for answer, streaming_start, speak, send_dtmf and hangup were written by symmetry with the documented ones. If the join does not work on your first test call, the documented alternative is a TeXML application that connects the call to the stream. This is the most likely thing to need a fix.
- **The shape of Ultravox tool parameters** (`staticParameters`) and the Ultravox messages path.
- **The Telnyx signed string for call events** (`timestamp|body`, as the vendor libraries do).
- **A real deployment.** The CI workflow in `.github/workflows/ci.yml` builds both Docker images and starts the compose stack on a GitHub runner, then checks that the API and the web sign in page answer. No deployment to a real host (Hetzner, Railway or Vercel) was done, and the three hosting guides were not followed on a real account. The Caddyfile and cloud-init were checked for valid syntax only.
- **A language model on a real call.** The agent in the demo and in the persona suite is a set of rules that reads directives from your prompt text, and it is labelled "offline rules, not a language model" on every screen. A real model path exists (`LLM_BACKEND=anthropic`, see "The live model path" below). It has run only against a local fake of the Anthropic endpoint (request shape, schema, guards) and against recordings made from that fake. It has never been run with a real key, so how a real model behaves on a call is UNVERIFIED.
- **How a voice sounds.** Nobody who built this can hear. Voice quality is for you to judge on a real test call.

## The live model path (UNVERIFIED live)

What is built and tested without an account (`apps/api/tests/test_model_path.py`, 22 tests):

- The model plays the agent one turn at a time and answers in a fixed JSON shape (what to say, which of the seven tools). The greeting with the AI disclosure is written by code, never by the model.
- What the person says is passed in as marked data. Words that look like the markers cannot close the block.
- Rules run around the model and cannot be talked out of it: a request to stop, a withdrawn consent, a machine or a phone menu are handled by the rules with no model call. A claim to be a person is replaced with the disclosure, a machine question always gets an honest answer, no price, no link, no leak of the instructions. A booking must use an offered time and a name, a text is dropped after a withdrawn consent, a key press must be the configured key and only once, and "booked" is not accepted without a real booking (the same check is in the end call tool, so it holds on a real voice call too, not only on the text path).
- There is no tool for placing a call, so no caller can make the agent dial anyone. A bad answer (wrong shape, unknown tool, unknown outcome code), the kill switch or an used up budget ends the call politely and marks it "needs review".
- Call summaries and the weekly summary go through the same wrapper; a summary with a number that was not in the facts is replaced by a plain one. The persona suite scorer is code, not a model: with a model agent, the caller is still scripted and the checks are still code.

What is not known: whether a real model keeps to these rules over a long, messy call, how it handles interruptions and silence, how long each turn takes (a voice call needs fast turns, and a model turn through a text path is not the Ultravox voice loop), and what it costs per call. The recorded answers in `data/llm_fixtures` were made from the fake server answering with the offline rules, so they show the replay path works, not how good a model is. The independent held out numbers in `CALLER-READER-EVAL.md` are for the offline rules only. When you have a key, run the same tool with a model reader before you trust one.

## The persona suite is not a model score

Dev set 14 of 14 (tuned against, so it proves little). Held out set 1: first run 12 of 14, then tuned, so no longer held out. Held out set 2: first run 7 of 14, not tuned at the time; the current code scores 14 of 14 on it after later reader changes, so it is spent too. The first runs are saved in `data/eval/`. Read `PERSONA-SUITE-EVAL.md`.

## Not legal advice

Rules for AI voices, consent, recording, calling hours and texting depend on place. `US-CALLING-CHECKLIST.md` lists what Ringlark does and what it cannot do for you.

## Shipped defaults you can change

These rules were decided as a safe starting point. They are not legal advice and your client may need different ones. Voicemail is off unless a campaign enables it with a message that says it is an AI, who is calling and why. Phone menus: hang up, or press one configured key once. 3 tries per person on different days, 09:00 to 17:00 in the person's time zone, weekdays, daily cap 50 (25 in the demo). Transfers 09:00 to 17:00 New York time, weekdays. Demo numbers are in the fictional 555 01xx range. Change any of them in the settings listed in `04-ENVIRONMENT-VARIABLES.md`.

## Other limits

- One campaign dials at a time per tick. It is a small dialer, not a call center.
- On a live call the rules are in the voice model's prompt, not in code that listens (see `13`). The tool side and the after call checks are code. A person can be kept on the line by a model that ignores its prompt until the call ends and the transcript is read.
- No email is read back: there is no inbox reader. A person who wants to stop email follow ups texts STOP (checked again at the moment an email is sent) or says so on a call (they go on the do not call list, which also stops emails). The email footer promises exactly that and no more: a STOP text ends texts and emails, it does not by itself put the number on the do not call list for calls.
- A call saved before ringing that shows no sign of life for 30 minutes is settled by the dial tick. If the voice engine knows it (it has an Ultravox id) it is moved to in progress and its transcript is read back, so a stop request said on it is still recorded; if it never reached the voice engine it is marked failed. Either way its attempt counts, so nobody is called twice by accident. The Ultravox call made for a crashed attempt is not cancelled (the adapter has no cancel).
- There is no unique database rule on (person, attempt). The in flight check and the saved row before ringing prevent a double dial, but a second worker started by mistake is not stopped by the database.
- An inbound caller's number is whatever caller ID says, and caller ID can be faked. Inbound calls are capped (`MAX_INBOUND_CALLS`, `MAX_INBOUND_PER_NUMBER_HOUR`) and the agent never reads a name back to them; an inbound caller has no time zone on file, so the app never texts one (no text is sent without a known local time, whatever the caller replied).
- No call recording or audio storage. The waveform in the screens is generated from turn times and says so.
- English only in the prompts and persona suite.
- The code that looks for a request to stop in a call transcript is a set of patterns and missed 9 of 24 and 6 of 21 must-stop lines on its first runs (see `13` and `CALLER-READER-EVAL.md`). A call that ends as needs review holds the person until someone has read it, which is a person doing the check the code cannot. Whether Ultravox returns the transcript right away when a call ends is UNVERIFIED: an empty one is read again for about 3 minutes and then flagged for a person.
- A booking that times out at Cal.com may or may not have been saved. The agent is told someone will follow up, the call is flagged, and it is not booked a second time on that call, so check the calendar for it.
- The Docker images and Postgres are named by a floating tag (`python:3.12-slim`, `node:22-slim`, `postgres:17`), so a rebuild can pull a newer image. Pin them by digest at release time if you need the same bytes every time. Docker on the Hetzner server comes from the Ubuntu package archive (`docker.io`, `docker-compose-v2`); the cloud-init was written that way but no server was created to try it.
- The web app sends a content security policy (same site only, no framing, no plugins) that still allows inline scripts (`unsafe-inline`). Removing that needs a per request nonce, which makes every page render on the server for each visit and changes how Next.js loads its own scripts. That change could not be tried in a browser here, so it was left out on purpose: a wrong nonce setup would leave every page blank. Until it is done, a script injected into a page would not be stopped by the policy, so the other defences (no user HTML is rendered, no third party scripts) are what protect the pages.
- **"Do not text me" said on a call.** The in call text tool cannot see what this person has said on this call: nothing in this code listens to a live call. It is the model's prompt that tells it not to text someone who says so. After the call the transcript is read, the request is recorded and no text is queued or sent to that number from then on, but a text the model sent during the call, against the prompt, is already out. A STOP text sent to your number is recorded at once and stops every later text and email.
- **Follow ups and bookings of unknown outcome.** A text, email or booking that ends in a timeout, a dropped line or a vendor server error (5xx) is held and never repeated by itself, because it may have gone through. A person confirms (a button on the Follow ups page; for a booking, the calendar is the check). If many do, look at the vendor's status page before you look at this code.
- **The number rules are not the whole phone system.** Extensions are refused, a `+1` number must be ten digits, and the Caribbean `+1` area codes are refused unless you name them, but a number from a country you allow can still be a premium or fraud number that is not on the built in list (`compliance.py`). The list is not complete.
- **Retention and erasure** work on what this app holds. They do not reach the CRM, Telnyx, Ultravox, Cal.com, the mail server or backups (guide 13, "Personal data"). Phone numbers stay in the call log and the consent records until you erase the person.
- A database file written by an earlier 1.0.1 build gets the new column and indexes when the API or worker starts (SQLite); on Postgres run `alembic upgrade head` (migration 0002).
- SQLite is fine to try. Use Postgres for real use.

## Round 4 notes

- **Open times on a live call (UNVERIFIED with a real model and the real Cal.com).** The prompt of every real call lists the next open times (at most 6, each as an ISO time with its UTC offset and said in the person's own time zone) and the tool `list_times` returns them again; a refused booking carries them too, and a time with no offset is refused (it would be read as UTC). The code that does this was tested with fake calendars only. Cal.com's own answer for `/v2/slots` (shape, time zone of the `start` values) is as the public docs describe it and has not been seen live, and how well a real model copies the value exactly is not known. If the calendar cannot be reached when the call starts, the prompt says so and the model must ask with `list_times`.
- **A vendor that fails.** A call that fails before the phone could ring does not use up a person's tries or the daily cap. After `DIAL_FAILURE_LIMIT` such failures in a row the dial tick stops, rests ten minutes and shows the reason on the Overview. If people were already held back as "suppressed" by an outage under an older build, the owner puts them back with `POST /api/campaigns/<id>/targets/restore` (never anyone on the do not call list, with a withdrawn consent, or with all their real tries used). A Telnyx or Ultravox that hangs still holds the single worker for its timeout (15 and 20 seconds) at most three times per tick.
- **The CRM.** A hung or unreachable CRM never costs a note: the queue keeps it. Only a refusal about that one note, or an answer nobody can read, counts as a try (three), and a note that waited seven days is moved with the others to a dead letter list (`GET /api/crm/dead-letters`, shown as a count on the Overview, put back by the owner with `POST /api/crm/dead-letters/<call>/retry`). Bookings that come from an inbound call are not written to the CRM: only outbound calls with a person in a list are. That is not built.
- **Countries.** An empty or unreadable `ALLOWED_CALLING_COUNTRIES` allows no country and shows a problem on the settings page; before, it allowed every country.
- **Unreadable vendor answers.** A 2xx answer from Cal.com, Telnyx, Ultravox or Twenty with a body that is not what the vendors' public docs describe is treated as an unknown outcome for a write (never repeated by itself, flagged for a person) and as a plain failure for a read. Nothing is retried blindly.
- **Voicemail (UNVERIFIED against live Telnyx).** A message is now spoken after the machine's greeting ends, not the moment it is detected: Ringlark waits for the event `call.machine.greeting.ended`, speaks, and records `voicemail_left` only when it receives `call.speak.ended`. The event names and the order of events were written from Telnyx's public docs and are not seen live. With no end of greeting within 60 seconds nothing is said and the line is closed; a message whose end is not confirmed within 90 seconds is not recorded as left (the call is `voicemail_no_message` with a note saying so). Whether a given machine's beep is detected is for you to test with a few real calls. **Dependency:** the dial request still asks Telnyx for the answering machine mode `detect_words`. Telnyx documents the modes premium, detect, detect_beep, detect_words and greeting_end, and which of them sends `call.machine.greeting.ended` was not confirmed here (the saved excerpt in `mock/contracts/telnyx` lists the modes and the detection event only). If your test calls show that the event never arrives, the fail safe applies (nothing is said and nothing is recorded as left); change the mode in `adapters/telnyx.py` to the one Telnyx documents for end of greeting and test again.
- **Callers who withhold their number** share a limit of their own (`MAX_INBOUND_ANONYMOUS_HOUR`, 30 an hour) and no longer use up one bucket that locks out every other private caller. Which value Telnyx sends for a withheld number (an empty field, the word "anonymous" or the placeholder number `+266696687`) is UNVERIFIED: all three are read as withheld.
- **Time zone against area code.** The calling hours use only the time zone in your list. An import now compares the area code of each `+1` number with the zone and flags a row that does not fit (about 300 area codes that lie inside one standard time zone are in the table; the others are not checked). It is a warning, not a block: people keep their number when they move. The owner must start such a campaign with `acknowledge_timezone_warnings`, outside demo mode. The check cannot find a wrong zone for a number whose area code is not in the table, or a person who lives where their area code says but whose row has the right zone for the wrong reason.
- **The daily cap** counts from midnight in `OFFICE_TIMEZONE`, not from midnight UTC (at 19:00 in New York in winter the UTC day had already changed). A campaign aimed at a different time zone from the office is still counted by the office's day.
- **An inbound booking** (a caller who books an appointment on a call they made) is not written to the CRM, and no follow up text or email is queued for it, because only outbound calls to a person in a list have a person record. Cal.com sends the confirmation mail to the address the caller gave: an address a caller types or spells out is not proven to be theirs, so a spoofed, mistyped or stranger's address could receive a Cal.com confirmation. The booking tool accepts one plain address only and a booking is made once per call, but Ringlark cannot tell whose address it is.
- **The QA queue** is paged with an offset (100 a page), so a call beyond the first 1000 can be reached and marked as read.
- **A recording notice** must contain the whole word "recorded", "recording", "record", "transcribe", "transcribed" or "transcribing"; the word "records" (as in medical records) no longer counts.
- **Answering an inbound call** now asks the calendar for the open times before the voice engine is set up. A hung Cal.com can therefore delay the answer by up to its 15 second timeout (a calendar that fails is not an error: the prompt tells the model to ask with `list_times`).
- **The commands in guides 10 and 13** (sign in, create an agent, a number, a campaign, import, erase) were checked against the routes by tests and read through; they were not run one by one on a fresh clone on a real host.
- **The web unit tests** (`pnpm --filter web test:unit`) are not run by the CI workflow in this repository, which the hub generates. Run them yourself before a release; the change is requested for the hub template.
